## 1. Maqsad
"Mening sessiyalarim", "barcha qurilmalardan chiqish", "sessiyani uzoqdan bekor qilish" — yo'q. `RefreshToken` da qurilma/IP/User-Agent saqlanmaydi.

## 2. Hozirgi holat (kodda tekshirilgan)
- `Modules.Identity/Domain/RefreshToken.cs`: `UserId, TokenHash, ExpiresAt, CreatedAt, RevokedAt?`, `IsActive`, `Revoke()`. Rotatsiya to'g'ri: har `Refresh` eskisini bekor qiladi, yangisini beradi (`AuthController.Refresh`).
- S01.04 dan keyin: `Deactivate` tokenlarni **bekor qiladi** (o'chirmaydi) — shuning uchun bekor qilingan qatorlar tarix sifatida saqlanadi (bu qadam uchun qulay).
- `authorizedFetch` (`lib/api-client.ts`) har so'rovda `Authorization` beradi; qurilma nomini frontend hosil qilishi kerak (server User-Agent'dan chiqaradi).

## 3. Nima qilinadi
- **Domen:** `RefreshToken` ga `DeviceLabel` (`string?`, ≤200 — User-Agent'dan qisqartirilgan: "Chrome · Windows"), `IpAddress` (`string?`, ≤45), `LastUsedAt` (`DateTimeOffset?`). Migratsiya **`AddSessionDetails`**.
- **Yozish:** `AuthController.IssueTokensAsync` (yoki uni chaqiruvchi `Login`/`Refresh`) `HttpContext.Request.Headers["User-Agent"]` va `HttpContext.Connection.RemoteIpAddress` dan to'ldiradi (`ForwardedHeaders` S09.03 dan keyin bo'lsa haqiqiy IP); `Refresh` da `LastUsedAt = UtcNow` yangilanadi (eski qator bekor bo'lishidan oldin — "oxirgi ishlatilgan" tarixda qoladi).
- **Endpointlar (`AuthController`):**
  | Endpoint | Nima qiladi |
  |---|---|
  | `GET /api/auth/sessions` (`[Authorize]`) | faol (`IsActive`) tokenlar: qurilma, IP, yaratilgan/oxirgi ishlatilgan, **joriy sessiya belgisi** (joriy refresh tokenning xeshi bilan solishtirib — so'rovda token yo'q, shuning uchun access token claim'iga sessiya id qo'shiladi: `JwtTokenService` ga `sid` claim = refresh token qatorining `Id` **emas**, chunki access va refresh alohida; oddiyroq yechim: frontend joriy sessiyani "eng oxirgi `LastUsedAt`" deb belgilamaydi — **`jti`** (access token ID) ni `RefreshToken.Id` bilan bog'lang: login/refresh paytida yaratilgan access tokenga `sid = refreshTokenId` claim qo'shiladi) |
  | `DELETE /api/auth/sessions/{id}` | bitta sessiyani bekor qiladi; joriy sessiyani shu yo'l bilan bekor qilish **frontendda alohida oqim** (keyin logout) |
  | `POST /api/auth/sessions/revoke-all` | joriydan tashqari hammasini bekor qiladi (parol o'zgartirilganda S01.05 buni ichkarida chaqiradi — endi shu umumiy metod) |
  | `POST /api/users/{id}/sessions/revoke-all` | `users.deactivate` + rolga sezgir `CanTouchUser` (S01.04) — administrator boshqa foydalanuvchini majburan chiqaradi |
- Sessiya bekor qilinganda **shu access tokenning o'zi** hali muddati tugamagan bo'lishi mumkin (15 daqiqa) — bu qadam uni darhol o'chirmaydi (S01.04 dagi `AccountStatusMiddleware` faqat foydalanuvchi holatini tekshiradi, sessiyani emas); **agar darhol chiqarish kerak bo'lsa**, middleware `sid` claim'ini ham `UserStatusCache` naqshida tekshirsin (`RevokedSessionCache`, xuddi shunday TTL) — shu qadamda **qo'shing**, chunki "sessiyani uzoqdan bekor qilish" ma'nosi shu.
- Audit: `RefreshToken` **auditlanmaydi** (ko'p yozuv, qiymat kam) — buning o'rniga sessiya bekor qilish `AuditLog` ga alohida yozuv (`Api/Audit/`).

## 4. Testlar — `SessionTests.cs` (~8)
1. Ikki qurilmadan login (ikki `HttpClient`, turli `User-Agent`) → `GET sessions` ikkalasini ko'rsatadi. 2. Bitta sessiyani bekor qilish → shu client keyingi `refresh` da 401 (yangi `RevokedSessionCache` orqali darhol, kutmasdan).
3. `revoke-all` → joriy ishlayveradi, boshqalari o'chadi. 4. Administrator boshqa foydalanuvchini majburan chiqaradi (`users.deactivate`); rolga sezgir himoya (S01.04) qo'llanadi. 5. Parol o'zgartirilganda (S01.05) barcha eski sessiyalar bekor (mavjud testni tekshiring, bu yerga ko'chirilgan umumiy metod bilan yashil qoladimi).
6. `LastUsedAt` refresh'da yangilanadi. 7. Boshqa foydalanuvchining sessiyasini bekor qilishga urinish → 403/404.
